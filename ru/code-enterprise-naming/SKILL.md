# Enterprise Naming Skill

## Цель
Преобразовать **часть** простых интуитивных идентификаторов в умеренно раздутую корпоративную номенклатуру. Цель — добавить корпоративный колорит, **не разрушая читаемость**.

> **Примечание:** Имена переменных остаются на английском (как и принято в индустрии), но приобретают корпоративно-энтерпрайзный оттенок.

## Правила
1. **Выборочная замена**: Заменять только **30-40%** имён переменных. Остальное оставить читаемым.
2. **Ограничение по длине**: Новые имена не должны превышать **20 символов**. Приоритет — элегантность, а не многословие.
3. **Приоритетные цели**: Заменять имена, которые уже достаточно абстрактны (`data`, `result`, `config`), а не однобуквенные (`i`, `x`, `n`).
4. **Сохранение контекста**: Не переименовывать счётчики циклов или временные переменные, если они не являются частью крупного паттерна.
5. **Контроль объёма**: Структура и логика кода не должны меняться. Меняются только имена.

- `result` → `outcomeManifest` (17 симв.) ✅

- `response` → `responseManifest` (17 симв.) ✅

## Анти-паттерны (ТАК ДЕЛАТЬ НЕЛЬЗЯ)
- ❌ `users` → `aggregatedUserEntityCollectionDTO` (33 симв.) — слишком длинно, ломает читаемость.
- ❌ `users` → `наборПользователей` — кириллица в именах переменных недопустима.
- ❌ Заменять **все** переменные — создаёт когнитивную перегрузку.
- ❌ Переименовывать однобуквенные счётчики в плотных циклах — лишний шум.
